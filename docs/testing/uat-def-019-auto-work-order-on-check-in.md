# UAT-DEF-019 — إنشاء أمر العمل تلقائيًا عند تسجيل الوصول

## النتيجة

READY — Customer check-in atomically creates and opens one work order using the branch default work-order warehouse without issuing inventory.

## الدورة

- سابقًا: تسجيل الوصول ثم إنشاء أمر عمل يدويًا واختيار المستودع.
- حاليًا: تسجيل الوصول للحجز `pending` أو `confirmed` ينشئ أمر عمل واحدًا من الحجز ويفتحه مباشرة.
- يظل مسار إنشاء أمر العمل اليدوي متاحًا للحالات الاستثنائية والبيانات القديمة.

## إعداد المستودع

أُضيف إعداد nullable باسم `default_work_order_warehouse_id` لإعدادات الفرع. لا يعرض ولا يقبل إلا مستودعًا نشطًا، غير نظامي، تابعًا لنفس الشركة والفرع، ومسموحًا له بصرف خامات أوامر العمل. لم يتم اختيار مستودع أو تعديل بيانات UAT تلقائيًا.

## الحماية والمعاملة

- يتم قفل الحجز داخل Transaction واحدة.
- عند فشل إنشاء أمر العمل تتراجع بيانات تسجيل الوصول كاملة.
- يُعاد استخدام `WorkOrderCreationService::fromAppointment()`.
- الطلب المتكرر يفتح أمر العمل النشط الموجود دون استهلاك رقم أو إنشاء خدمات أو فحص مكرر.
- فشل قواعد التشغيل يعرض رسائل عربية بدل خطأ 500.

## المخزون والمحاسبة

إنشاء أمر العمل يحدد المستودع وينقل الخدمات والخامات المتوقعة فقط. لا ينشئ Stock Movement أو صرف مخزون أو قيدًا محاسبيًا.

## الاختبارات

- أضيف `AppointmentCheckInWorkOrderTest` لتغطية صلاحية المستودع، منع التشغيل دون إعداد، Atomic rollback، إنشاء أمر واحد فقط، نقل البيانات والخدمات، إنشاء فحص draft، وعدم تحريك المخزون أو المحاسبة.
- حُدّث اختبار Phase 9 القديم ليتوافق مع الدورة الجديدة.
- تعذر إكمال اختبارات قاعدة البيانات لأن قاعدة `seven_ways_testing` الحالية تُرجع MariaDB 1036 (الجداول للقراءة فقط) ولا تحتوي العمود الجديد.

## Manual UAT

لم تُعدّل بيانات UAT. بعد تحديد المستودع يدويًا من إعدادات الفرع: أكّد الحجز، سجّل الوصول، وتحقق من فتح أمر العمل وحالة `in_progress` وعدم تغير أرصدة المخزون. إعادة إرسال الطلب يجب أن تفتح نفس أمر العمل.
