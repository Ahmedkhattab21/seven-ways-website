# Three-role branch operating model

## الملخص

يعتمد التشغيل اليومي على ثلاثة أدوار أعمال:

| الدور | النطاق | المسؤولية |
|---|---|---|
| مسؤول الفرع (`branch_manager`) | فرع واحد | المبيعات والتحصيل والخزينة والمخزون والمشتريات اليومية |
| المحاسب (`accountant`) | الشركة وكل الفروع | المراجعة والترحيل والموردون والبنوك والضرائب والتقارير |
| المدير العام (`general_manager` / `company_owner`) | الشركة وكل الفروع | الإدارة والاعتمادات الحساسة وإعدادات الشركة |

يبقى `system_admin` للدعم التقني. الأدوار `sales`, `cashier`, `receptionist`,
`warehouse_keeper`, `technician`, `quality_controller` محفوظة تاريخيًا، لكنها مصنفة
في الواجهة كأدوار قديمة ولا تظهر عند تعيين دور جديد.

## مسؤول تشغيل الفرع

- أضيف `branches.responsible_user_id` كعلاقة اختيارية وفريدة، مع
  `responsible_assigned_at`.
- التعيين يقبل مستخدمًا نشطًا من نفس الشركة يملك `branch_manager`.
- لا يمكن تعيين المستخدم نفسه لفرعين أو وجود أكثر من مسؤول حالي للفرع.
- التغيير يتم داخل Transaction، يسحب وصول المسؤول السابق دون حذفه أو تعديل مستنداته،
  ويكتب Audit Log قبل/بعد.
- مسؤول الفرع يحصل على فرعه وحده في `user_branch_access` ولا يملك اعتماد عملياته.
- يمكن إنشاء حساب مسؤول جديد مع الفرع داخل Transaction واحدة، أو تعيين حساب قائم من
  صفحة تعديل الفرع.

## الصلاحيات والقوائم

`ThreeRoleOperatingModelSeeder` يعمل في نهاية Seeders المرجعية ليمنع Seeders القديمة
من إعادة توسيع الأدوار:

- مسؤول الفرع: دورة العملاء والمبيعات، تشغيل الخزينة، طلبات الشراء والاستلام والمخزون
  داخل فرعه، دون دليل الحسابات أو القيود أو إدارة الفروع والمستخدمين.
- المحاسب: نطاق شركة مركزي للمراجعة والموردين والخزينة والبنوك والمحاسبة والتقارير،
  دون إدارة المستخدمين أو الفروع، ودون فتح/عد/إغلاق جلسة بدل مسؤول الفرع.
- المدير: كل الوحدات المفعلة وإدارة الشركة والاعتمادات.

القائمة تبقى Permission-driven، وFeature Flags من `config/modules.php` تمنع عرض أو
الوصول المباشر للعملاء المحتملين والحجوزات وأوامر العمل والفنيين والجودة وإعادة العمل
والتسليم والضمانات.

## الدورات

### البيع

عميل ← سيارة اختيارية ← عرض سعر اختياري ← فاتورة ← طباعة/تحصيل ← سند قبض ← ترحيل.
لا تعتمد هذه الدورة على حجز أو أمر عمل أو فني أو جودة.

### المشتريات

طلب شراء الفرع ← اعتماد عند تجاوز الحد ← أمر شراء ← استلام الفرع ← فاتورة المورد
ودفعها بواسطة المحاسب.

### الخزينة

مسؤول الفرع يفتح ويعد وينفذ ويرسل الجلسة. المحاسب يراجع الفروق. المدير يدخل فقط عند
تجاوز حد الاعتماد. تظل قواعد Approval Engine وSeparation of Duties الحالية مصدر
القرار، ولا توجد أرقام حسابات ثابتة في التعديل.

## حماية البيانات

- Migration إضافية Forward-only؛ لا حذف ولا Backfill تلقائي لمسؤولين قدامى.
- لم تُحذف أدوار أو مستخدمون أو مستندات أو جداول تاريخية.
- Rollback يزيل العمودين والعلاقة فقط، ولا يحذف المستخدمين.

## UAT والاختبارات

- أضيف `ThreeRoleBranchOperatingModelTest` لتغطية التفرد، منع المستخدم من فرعين،
  تغيير المسؤول مع Audit، عزل الفرع، إخفاء selector، وفصل صلاحيات المحاسب.
- تعذر تطبيق Migration لأن MariaDB أعادت: `Table 'branches' is read only`.
- نتيجة الاختبار المستهدف قبل تطبيق Migration: `1 passed`, `3 failed` بسبب غياب
  `responsible_user_id` فقط، وليس بسبب منطق Assertions.
- نجح PHP lint وPint وRoute list وBlade cache و`git diff --check`. يجب تشغيل الاختبارات بعد إصلاح MariaDB
  بطريقة غير مدمرة وأخذ Backup.

## حالة UAT

لم يُنشأ حساب UAT تلقائيًا حتى لا تُفرض كلمة مرور معروفة. بعد تطبيق Migration يمكن
إنشاء «مسؤول الفرع الرئيسي UAT» من صفحة إنشاء/تعديل الفرع وتعيينه إلى `CAI-MAIN`.
بيانات `accountant@sevenways.test` و`owner@sevenways.test` لم تتغير.
